\begin{abstract}
Large-scale Mixture-of-Experts (MoE) training runs for weeks on thousands of GPUs, and rank failures are common during such runs. Existing mechanisms typically recover by restarting from a globally consistent checkpoint, treating replicated non-expert state and rank-unique expert state as one monolithic object.
We present \textbf{MoEGambit}, a recovery-side framework for Megatron-LM that exploits this state heterogeneity through an explicit runtime contract. The contract has three checkable components: a safe-point repair controller that prevents partial optimizer commits, an expert-weighted staleness density $\Phi'(t)$ that defines when partial repair is admissible, and a guarded reintegration state machine with structured logs.
When the contract admits hybrid repair, MoEGambit pulls current non-expert state from a healthy data-parallel peer and loads only the failed rank's expert shard from checkpoint, eliminating replay. A weights-first/optimizer-later two-phase protocol further overlaps optimizer restoration with resumed computation.
On Qwen3-30B-A3B and DeepSeek-V2-Lite, MoEGambit reduces raw recovery latency by $20.6\%$--$55.0\%$ and yields a $36.9\times$ replay-inclusive speedup. Across single-, repeated-, and burst-failure scenarios admitted by the contract, paired evaluation finds no post-recovery degradation in validation loss, perplexity, or downstream zero-shot accuracy.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Training a large language model is a weeks-long, multi-thousand-GPU software process in which failures are common. Llama~3 reports a failure roughly every 45\,minutes on a 16{,}384-GPU cluster~\cite{dubey2024llama3}; MegaScale documents hundreds of failure modes in a 10K-GPU deployment~\cite{jiang2024megascale}; and the OPT-175B logbook records weeks of human intervention~\cite{zhang2022opt}. The standard recovery mechanism, \emph{checkpoint restart}, reloads the latest globally consistent snapshot and replays all lost iterations, regardless of which state was actually invalidated. At modern failure rates, even modest per-failure outages accumulate into substantial aggregate GPU time over a training run.

Sparse Mixture-of-Experts (MoE) architectures---used by Mixtral~\cite{jiang2024mixtral}, DeepSeek-V2/V3~\cite{deepseekv2,deepseekv3}, and Qwen3-MoE~\cite{qwen3report}---make this cost structural. In dense training, a failed replica can often be reconstructed from a healthy data-parallel peer because the full model state is replicated. In MoE training, only the \emph{non-expert} state (attention, embedding, router) is replicated in this way; expert parameters and optimizer moments are commonly rank-unique after expert sharding. Restart ignores this split: it rolls back the whole job, reloads all checkpointed state, and replays every lost iteration.

Prior fault-tolerant training systems reduce checkpoint cost~\cite{mohan2021checkfreq,nicolae2020deepfreeze,eisenman2022check,wang2023gemini,wang2024reft,wan2024bytecheckpoint}, adapt topology around failures~\cite{thorpe2023bamboo,jang2023oobleck,gandhi2024recycle}, or recover dense replicas from peers~\cite{zhang2025flashrecovery}. However, they do not address MoE's recovery-side asymmetry. Checkpoint/replica systems preserve checkpoint-consistent restart semantics; topology-adaptation systems rely on rank interchangeability; dense peer recovery assumes the failed rank's full state has a live peer. MoE violates that assumption selectively: non-expert state can be peer-recovered, while rank-unique expert state must come from checkpoint. The only MoE-specific fault-tolerance system we are aware of, MoC-System~\cite{cai2024moc}, optimizes save-side cost through Partial Experts Checkpointing but still resumes from checkpoint state. This leaves a recovery-side gap: no existing system combines peer recovery for replicated MoE state with checkpoint repair for rank-unique experts while bounding the quality risk introduced by partial repair.

\textbf{Key observation.} Peer recovery is not unique to MoE, but MoE recovery is \emph{partially} peer-recoverable. Non-expert parameters (attention, embedding, router) are replicated across the data-parallel dimension and can be pulled from a healthy peer, just as in dense peer recovery. Expert parameters and optimizer state, however, are EP-sharded and may be rank-unique. When a rank fails, the replacement can therefore pull current-step non-expert state from a healthy peer and load only the rank-local expert shard from the latest checkpoint---eliminating replay while reducing disk I/O to the rank-unique expert volume.

Hybrid recovery raises a software-engineering question beyond I/O cost. It resumes with current non-expert state but checkpoint-aged expert state, so the restored experts are stale by $\Delta=t-c$ iterations; repeated recoveries can accumulate this staleness across the expert population. Without a runtime-checkable specification of when the hybrid path is safe, operators face an unaudited tradeoff between speed and model quality. Following the self-adaptive-systems view of monitored, auditable runtime adaptation~\cite{kephart2003autonomic,garlan2004rainbow,salehie2009selfadaptive}, MoE recovery should be specified against the post-recovery training trajectory rather than only against process liveness.

We present \textbf{MoEGambit}, a recovery-side framework for MoE training integrated into Megatron-LM~\cite{narayanan2021megatron}. MoEGambit admits hybrid recovery only when expert staleness is bounded and logged. It introduces an explicit recovery contract with three artifacts: a safe-point repair controller that prevents partial optimizer commits~(R1), an expert-weighted staleness density $\Phi'(t)$ with an empirically calibrated quality threshold~(R2), and a guarded reintegration state machine with structured logs~(R3). The contract defines the conditions under which hybrid repair is admissible. MoEGambit then contributes two recovery mechanisms: a MoE-aware hybrid repair path that pulls current non-expert parameters from a healthy peer and loads only the failed rank's expert shard from checkpoint, and a weights-first/optimizer-later two-phase recovery protocol that overlaps optimizer restoration with resumed computation.

We evaluate MoEGambit on Qwen3-30B-A3B~\cite{qwen3report} (128 experts, 64 H20 GPUs) and DeepSeek-V2-Lite~\cite{deepseekv2} (64 experts) under SE experimentation standards: every recovered run is paired with a NoFault baseline sharing identical seed, data order, checkpoint, and injected failure step~\cite{wohlin2012ese,arcuri2014hitchhiker}, so residual quality differences can be attributed specifically to recovery rather than to seed noise. \textbf{MoEGambit reduces raw recovery latency by $20.6\%$--$55.0\%$ and eliminates replay cost entirely ($36.9\times$ end-to-end speedup). Across single-, repeated-, and burst-failure scenarios admitted by the contract, paired tests show no statistically detectable degradation in validation loss or perplexity; in the 50-run single-failure heatmap, 44/50 runs fall within the NoFault $\pm2\sigma_{\text{base}}$ band, and downstream zero-shot accuracy remains indistinguishable from full restart.}

This paper makes three contributions:
\begin{itemize}
    \item \textbf{Runtime recovery contract.} Three SE artifacts---safe-point invariant~(R1), expert-weighted staleness density $\Phi'(t)$ with an empirically calibrated quality threshold~(R2), and a guarded reintegration state machine with structured audit logs~(R3)---that separate \emph{when} hybrid repair is permitted from \emph{how} state is reconstituted (\S\ref{sec:moegambit}).
    \item \textbf{Hybrid repair and two-phase recovery.} A recovery-side mechanism that pulls DP-replicated non-expert state from a healthy peer at step $t$ and loads only EP-sharded expert state from a per-rank checkpoint shard at step $c$, plus a weights-first/optimizer-later protocol that overlaps optimizer restoration with resumed training (\S\ref{sec:mechanism}--\S\ref{sec:twophase}).
    \item \textbf{Paired fault-injection evaluation.} A reproducible benchmark on Qwen3-30B-A3B and DeepSeek-V2-Lite with paired NoFault baselines following SE experimentation guidelines~\cite{wohlin2012ese,arcuri2014hitchhiker}, demonstrating $20.6\%$--$55.0\%$ recovery-latency reduction, $36.9\times$ end-to-end speedup, and no statistically detectable quality degradation across six RQs (\S\ref{sec:eval}).
\end{itemize}

\section{Background and Motivation}
\label{sec:background}

We first define the MoE state classes that make partial recovery possible, then show why checkpoint restart leaves this structure unused.

\subsection{Concepts: MoE Training as a Heterogeneous-State Distributed Program}
\label{sec:bg-concept}

A distributed MoE training job~\cite{lepikhin2021gshard,fedus2022switch,rajbhandari2022deepspeedmoe,hwang2023tutel,gale2023megablocks} is a long-running, stateful, multi-process program executing collective communication on tens to thousands of GPUs. Unlike dense Transformers, MoE training maintains a \emph{heterogeneous state} that we partition along its data-parallel (DP), tensor-parallel (TP), pipeline-parallel (PP), and expert-parallel (EP) axes (Table~\ref{tab:state-provenance}):
\begin{itemize}
    \item \emph{Replicated state.} Non-expert layers (attention, embedding, layer normalization) and router weights are replicated across every DP rank that owns the same PP/TP coordinate. At any iteration $t$, at least one healthy peer holds the current-step value.
    \item \emph{Sharded expert state.} Expert weights and their AdamW first/second moments are partitioned across EP ranks. In a $128$-expert, EP$=8$ layout without expert replication, each rank exclusively owns a fixed subset of $128/8=16$ experts; no peer holds a current in-memory replica.
    \item \emph{Runtime metadata.} The expert directory, the dispatch topology used by all-to-all routing~\cite{he2022fastermoe,zhai2023smartmoe}, and the process-group view are derived from the rank layout and become stale the moment any rank is replaced.
\end{itemize}

\noindent\textbf{Expert Data Parallelism (EDP).}
The degree to which each expert is replicated across the cluster is captured by the \emph{Expert Data Parallelism} (EDP) degree, defined as $\text{EDP}=W/(\text{TP}\times\text{PP}\times\text{EP})$, where $W$ is the total number of ranks.
When $\text{EDP}=1$, every expert shard exists on exactly one live rank; when $\text{EDP}>1$, a failed expert shard may have a surviving peer copy, analogous to the peer copy used for non-expert parameters.
EDP$=1$ is the most constrained recovery operating point because every expert shard is rank-unique. In our evaluated Qwen3-30B-A3B layout, $W=64$, TP$=1$, PP$=8$, and EP$=8$, so $\text{EDP}=64/(1\cdot8\cdot8)=1$ even though the model has 128 experts; each EP rank owns 16 experts within its pipeline stage.
This operating point is resource-driven: large expert counts already distribute memory across ranks, while extra expert replication multiplies expert and optimizer memory with no compute benefit because each token activates only $K\!\ll\!E$ experts. It is also the setting in which MoE recovery differs from dense recovery: the expert portion of a failed rank has no live peer and must be restored from checkpoint.
Fig.~\ref{fig:edp-distribution} illustrates this distinction.

\subsection{Existing Flow: Checkpoint Restart and the Hidden Risk of Partial Recovery}
\label{sec:bg-flow}

\textbf{Motivating example.} In our 64-GPU Qwen3-30B-A3B job, a failure detected at step $t\!=\!200$ with the latest checkpoint at $c\!=\!100$ causes standard Megatron-LM to reload a 56\,GB distributed checkpoint and replay 100 iterations, for an outage of $\sim$1067\,s. The failed rank, however, owns only 16 of 128 experts; non-expert layers and the other 112 experts remain live on healthy ranks. A MoE-aware recovery path can therefore pull 3.2\,GB of non-expert state from a peer, load only the failed rank's expert shard, and resume at step $t$ in 29\,s with no replay. This opportunity also introduces a quality risk: the recovered experts are stale by $\Delta=t-c$ iterations.

Production LLM training commonly uses \emph{checkpoint restart}~\cite{narayanan2021megatron,dubey2024llama3,jiang2024megascale}: on a failure, the job reloads the most recent globally consistent snapshot at step $c$ and replays the $t-c$ lost iterations. Classical rollback-recovery and checkpoint-interval analyses~\cite{elnozahy2002survey,young1974first,daly2006higher} show that the optimal checkpoint interval scales as $\tau^{*}\!\approx\!\sqrt{2CM}$, where $C$ is the per-checkpoint cost and $M$ is the mean time between failures; with $M$ collapsing to tens of minutes on 10K-GPU clusters~\cite{dubey2024llama3,jiang2024megascale}, repeated failures can consume substantial aggregate GPU-hours in checkpoint I/O and replay.

Restart treats the entire job as a single all-or-nothing state object. Table~\ref{tab:state-provenance} shows why this is wasteful: a single failed rank invalidates only its EP-sharded expert state, while the DP-replicated non-expert state of every other rank at the same PP/TP coordinate remains current at step $t$. A natural alternative is \emph{hybrid recovery}: synchronize non-expert state from a healthy DP peer at the current step, and load only the rank-local experts from the latest checkpoint shard at step $c$. Hybrid recovery, however, introduces a side effect that restart does not: the recovered rank's expert state is stale by $\Delta = t-c$ iterations relative to the rest of the model.

This staleness is not a binary defect---restored experts still produce valid forward/backward signals---but it can perturb the auxiliary-loss-driven balancing dynamics of MoE training~\cite{shazeer2017outrageously,fedus2022switch,zoph2022stmoe,komatsuzaki2023sparse}. The risk has two dimensions: a \emph{per-event} gap $\Delta$ for the experts owned by the failed rank, and a \emph{window-level} debt accumulated by repeated hybrid recoveries across different expert shards. A recovery system that admits partial repair therefore needs a runtime-checkable bound on accumulated staleness, not only a fast mechanism.


\textbf{Problem statement.} MoEGambit receives a fail-stop event $\langle r,t,c\rangle$ from the cluster watchdog, where $r$ is the failed logical rank, $c$ is the latest checkpoint, and $t$ is the first step that should execute after safe-point handling. If a failure is detected mid-iteration, R1 discards that in-flight iteration and advances $t$ to the next valid step; thus $\Delta=t-c$ counts the iterations that checkpoint restart would replay. MoEGambit must choose either \textsc{Restart}, which restores all state from checkpoint and replays $t-c$ iterations, or \textsc{Hybrid}, which restores current non-expert state from a peer and expert state from the failed rank's checkpoint shard. In both cases, the first post-recovery \texttt{optimizer.step()} must be a valid AdamW update: no gradient may be applied to uninitialized or partially restored parameters.

\textbf{Requirements.} We formulate the recovery path as a contract with three SE-style requirements. \textbf{R1} defines a safe repair point and gates optimizer commits so a mid-step failure cannot corrupt model state. \textbf{R2} specifies hybrid eligibility through a quantitative, $O(1)$ guard that captures per-event and accumulated staleness. \textbf{R3} records every decision, guard input, latency segment, and state-machine transition for post-hoc auditability. MoEGambit assumes fail-stop rank failures, at least one available checkpoint, a healthy DP peer for the failed rank's non-expert state, and a replacement/hot-spare GPU; if the peer condition fails, the policy chooses \textsc{Restart}.

\section{Approach}
\label{sec:moegambit}

\subsection{Overview}
\label{sec:arch}

MoEGambit is a runtime recovery layer that intercepts rank-failure events and reconstitutes the replacement rank's state from the most current available source for each state class, without rolling back the rest of the job. Fig.~\ref{fig:moegambit-overview} summarizes the runtime architecture. The design separates \emph{what is guaranteed} (the recovery contract, R1--R3) from \emph{how state is repaired} (the hybrid restoration mechanism and two-phase protocol), so the contract can be audited independently of the implementation.

\begin{figure*}[!t]
\centering
\includegraphics[width=0.76\textwidth]{moegambit_runtime_architecture.pdf}
\caption{MoEGambit runtime architecture. On a rank failure, R1 establishes a safe repair point, R2 chooses \textsc{Hybrid} or \textsc{Restart}, the hybrid path restores replicated and expert state from different sources, and R3 logs the guarded reintegration trace.}
\label{fig:moegambit-overview}
\end{figure*}

The framework executes five components on each failure event (Fig.~\ref{fig:moegambit-overview}):
\begin{enumerate}
    \item \emph{Failure detection.} An external watchdog emits a failure event $\langle r,t,c\rangle$ identifying the failed rank, the current training step, and the latest checkpoint step.
    \item \emph{Safe-point repair controller} (\S\ref{sec:safepoint}, R1). Installs an optimizer commit guard so no rank applies gradients computed during recovery.
    \item \emph{Staleness-density guarded policy} (\S\ref{sec:policy}, R2). Evaluates the $O(1)$ guard $\Phi'(t)$ and returns a deterministic decision $\pi(t)\!\in\!\{\textsc{Hybrid},\textsc{Restart}\}$. If the projected staleness density exceeds the empirical quality threshold, MoEGambit falls back to checkpoint restart.
    \item \emph{MoE-aware hybrid restoration and two-phase protocol} (\S\ref{sec:mechanism}--\S\ref{sec:twophase}). Pulls non-expert state from a healthy DP peer at step $t$ (path~P), loads rank-local experts from the checkpoint shard at step $c$ (path~C), and overlaps optimizer-state restoration with resumed computation.
    \item \emph{Reintegration state machine and structured logs} (\S\ref{sec:obs}, R3). Advances the replacement rank to \texttt{HEALTHY} and emits a structured record linking policy inputs, latencies, and state-machine transitions.
\end{enumerate}

\subsection{Safe-Point Repair Controller (R1)}
\label{sec:safepoint}

R1 defines a single program point at which repair may run, with one invariant: no optimizer commit may use gradients computed under \texttt{RECOVERING}. On a failure event $\langle r,t,c\rangle$, the controller atomically marks $r$ and its experts as \texttt{RECOVERING}, installs a pre-AdamW commit guard on every rank, and marks the current iteration as \texttt{DISCARD}. Any rank reaching \texttt{optimizer.step()} under \texttt{DISCARD} skips the update; in-flight gradients are dropped. Training then resumes through hybrid repair (\S\ref{sec:mechanism}) or restart, and the controller logs the safe-point status.

\subsection{Staleness-Density Guarded Policy (R2)}
\label{sec:policy}

R2 is an $O(1)$ guard $\Phi'(t)$ and a deterministic decision $\pi(t)\!\in\!\{\textsc{Hybrid},\textsc{Restart}\}$ over the failure event $\langle r,t,c\rangle$, the window staleness debt $S(t)=\sum_{h\in\mathcal{H}_W(t)}|E_h|\Delta_h$, the predicate $\textsc{PeerAvail}(r,t)$, and thresholds $(\Delta_{\min},\Delta_{\max},\Phi_{\max})$ calibrated in \S\ref{sec:eval}. Here $\mathcal{H}_W(t)$ is the set of previously admitted hybrid events in the window $[t\!-\!W,t)$, $E_h$ is the expert set restored by event $h$, and $\Delta_h$ is its checkpoint gap; thus $S(t)$ has units of expert-iterations. The projected density assuming hybrid is
\begin{equation}
    \label{eq:phi-prime}
    \Phi'(t) \;=\; \frac{S(t) \,+\, |E_{\text{new}}|\, \Delta}{N_{\text{expert}}\cdot W},
\end{equation}
where the denominator $N_{\text{expert}}\!\cdot\!W$ normalizes the maximum debt to 1, so $\Phi'(t)\!\in\![0,1]$. The running aggregate $S(t)$ is maintained as a single scalar: on each hybrid event $h$ entering the window, add $|E_h|\Delta_h$; on each event leaving the window (older than $W$ iterations), subtract the same product---yielding $O(1)$ per-iteration bookkeeping. When multiple ranks fail simultaneously, each failed rank contributes its own $|E_h|\Delta_h$ term to $S(t)$ before the policy is evaluated for the next rank.

\textbf{Intuition.} The guard is a monitorable exposure budget, not a claim of global convergence. A hybrid event exposes $|E_h|$ experts to weights that are $\Delta_h$ iterations behind the rest of the model; repeated events expose more experts for longer. Charging each event by $|E_h|\Delta_h$ captures both factors, and normalizing by $N_{\text{expert}}\!\cdot\!W$ makes $\Phi'(t)$ comparable across model sizes and window lengths. The threshold $\Phi_{\max}\!=\!10^{-2}$ (\S\ref{sec:eval}) is calibrated against the observed failure-free noise floor.

The decision is
\begin{equation}
    \label{eq:policy}
    \pi(t) \;=\;
    \begin{cases}
        \textsc{Hybrid}, & \text{if } \textsc{PeerAvail}(r,t) \;\wedge\; \\
                         & \quad \Delta_{\min} \leq \Delta \leq \Delta_{\max} \;\wedge\; \\
                         & \quad \Phi'(t) \leq \Phi_{\max}, \\[2pt]
        \textsc{Restart}, & \text{otherwise}.
    \end{cases}
\end{equation}
Algorithm~\ref{alg:policy} encodes the same logic and records the first failing guard on every fallback. The three thresholds play distinct roles: $\Delta_{\min}$ is a cost-benefit lower bound that avoids hybrid repair when the replay gap is too small to offset its coordination cost; $\Delta_{\max}$ is a per-event staleness cap on any single recovered expert shard; and $\Phi_{\max}$ is a window-level cap on accumulated expert exposure. Each threshold traces to a measurable source: $\Delta_{\min}$ from the $T_{\text{load}}\!:\!T_{\text{hybrid}}\!:\!T_{\text{iter}}$ ratio, $\Delta_{\max}$ from the checkpoint interval bounded by Young/Daly~\cite{young1974first,daly2006higher}, $\Phi_{\max}$ from the guard-disabled quality sweep, and $\textsc{PeerAvail}$ from the live process group. The log entry contains $\langle\pi(t),\text{reason}\rangle$ and $(\Delta,|E_{\text{new}}|,S(t),\Phi'(t))$ (\S\ref{sec:obs}); the compact reason labels identify peer unavailability, the two gap guards, the exposure guard, and the admitted hybrid path.

\begin{algorithm}[!b]
\caption{Guarded recovery decision $\pi(t)$.}
\label{alg:policy}
\begin{algorithmic}[1]
\Require event $\langle r,t,c\rangle$; debt $S(t)$
\Require thresholds $(\Delta_{\min},\Delta_{\max},\Phi_{\max})$; \textsc{PeerAvail}
\Ensure recovery decision and first-failing reason
\State $\Delta \gets t-c$; $e \gets |E_{\text{new}}(r)|$
\State $\rho \gets (S(t)+e\Delta)/(N_{\text{expert}}W)$
\If{$\neg\,\textsc{PeerAvail}(r,t)$}
    \State \Return $(\textsc{Restart},\textsc{NoPeer})$
\ElsIf{$\Delta < \Delta_{\min}$}
    \State \Return $(\textsc{Restart},\textsc{SmallGap})$
\ElsIf{$\Delta > \Delta_{\max}$}
    \State \Return $(\textsc{Restart},\textsc{LargeGap})$
\ElsIf{$\rho > \Phi_{\max}$}
    \State \Return $(\textsc{Restart},\textsc{HighDebt})$
\Else
    \State \Return $(\textsc{Hybrid},\textsc{Admit})$
\EndIf
\end{algorithmic}
\end{algorithm}

\subsection{Theoretical Rationale for the Guard}
\label{sec:guard-rationale}

The recovery contract is the monitorable safety condition under which MoEGambit may choose the fast path. For every recovery event, hybrid recovery implies all three guards:
\begin{equation}
\label{eq:runtime-contract}
\begin{aligned}
\pi(t)=\textsc{Hybrid} \Rightarrow{}&
\textsc{PeerAvail}(r,t)\\
&{}\wedge\;\Delta_{\min}\leq\Delta\leq\Delta_{\max}\\
&{}\wedge\;\Phi'(t)\leq\Phi_{\max},\quad \forall t.
\end{aligned}
\end{equation}
R3 logs the witness for each conjunct, so the contract is checkable online and auditable offline. The threshold $\Phi_{\max}$ is empirical, but the form of $\Phi'(t)$ follows from a first-order exposure bound.

\noindent\textbf{Proposition 1 (expert-exposure bound).}
Assume that, within a recovery window, the monitored MoE loss component $\ell_{\text{aux}}$ is $L_{\text{aux}}$-Lipschitz in each expert state, and a normal step changes any expert by at most $G$ in the same norm. If event $h$ restores expert set $E_h$ from checkpoint step $c_h$ and resumes at $t_h$, then $\Delta\ell_h \leq L_{\text{aux}}G\,|E_h|\,(t_h-c_h)$; over the window, $\sum_h\Delta\ell_h \leq L_{\text{aux}}G\,S(t)$, and the projected bound is proportional to $N_{\text{expert}}W\Phi'(t)$. The bound follows from Lipschitz continuity and the telescoping drift $\|\theta_e(t_h)-\theta_e(c_h)\|\leq G(t_h-c_h)$. Thus $\Phi'(t)$ is a normalized upper bound on stale-expert exposure under the stated smoothness assumption; it is not a standalone convergence theorem.

\subsection{MoE-Aware Hybrid State Restoration}
\label{sec:mechanism}

On $\pi(t)=\textsc{Hybrid}$, the replacement rank reconstitutes its state by reading each state class from its most current available source (Table~\ref{tab:state-provenance}), so I/O scales with the rank-unique expert volume rather than the full distributed checkpoint. Two paths run concurrently. \emph{Path~P (peer pull, replicated state):} synchronize current-step non-expert parameters (and DP-replicated optimizer state) from a healthy peer at the same PP/TP coordinate via a single P2P broadcast over NCCL/Gloo, completing in tens of milliseconds. \emph{Path~C (shard read, sharded expert state):} load rank-$r$'s experts from the per-rank shard at step $c$ with no collectives. The recovered rank is intentionally mixed: non-expert state reflects step $t$, while experts and their optimizer state are stale by $\Delta$---the quantity bounded by $\Phi'(t)$ in (\ref{eq:phi-prime}) (Fig.~\ref{fig:moegambit-overview}, step 4a).

\subsection{Two-Phase Recovery Protocol}
\label{sec:twophase}

The two-phase protocol reduces time-to-resume by overlapping path~C's optimizer-state read with resumed forward/backward, while forbidding commits on uninitialized expert slots. \emph{Phase~A (weights first)} restores non-expert state and expert weights, then rejoins under an \emph{update barrier}: forward/backward contributes to the global loss, but gradients for affected experts are buffered. \emph{Phase~B (optimizer later)} restores non-expert and expert moments in parallel; when it completes, the barrier releases and buffered gradients are applied via one AdamW step. The barrier reuses the pre-\texttt{step()} hook of \S\ref{sec:safepoint}, so R1 holds throughout. The log records $T_{\text{TTR}}$ and $T_{\text{TTFR}}$; their gap is the latency saved over single-phase restart. Because the protocol controls \emph{when} optimizer state attaches, not \emph{where} bytes come from, \S\ref{sec:rq1}'s $2{\times}2$ factorial tests it independently of hybrid restore.

\subsection{Reintegration State Machine and Structured Logs (R3)}
\label{sec:obs}

R3 requires that every recovery decision and its downstream model-quality outcome be traceable. We realize R3 through two mechanisms: a guarded state machine that enforces the reintegration protocol, and a structured log that records the inputs and outputs of each recovery event.

\textbf{Guarded state machine.} Each replacement rank advances through a four-state linear protocol:
\begin{equation}
\label{eq:state-machine}
\texttt{RECOVERING} \xrightarrow{g_1} \texttt{REPAIRED} \xrightarrow{g_2} \texttt{BARRIER} \xrightarrow{g_3} \texttt{HEALTHY},
\end{equation}
where each transition is gated by a guard predicate:
\begin{itemize}
    \item $g_1$: state restoration complete---all state classes (non-expert via path~P, experts via path~C) have been loaded and verified against their source checksums.
    \item $g_2$: dispatch topology re-derived---the expert directory and all-to-all routing tables have been recomputed to reflect the replacement rank's position in the EP layout.
    \item $g_3$: optimizer state attached and update barrier released---Phase~B of the two-phase protocol (\S\ref{sec:twophase}) has completed, and the buffered gradients have been applied.
\end{itemize}
Because every transition requires its guard to hold, the state machine rejects premature reintegration---e.g., routing tokens to an expert whose optimizer state has not yet been restored.

\textbf{Structured recovery log.} On each recovery event, the state machine emits one record with policy inputs ($\Delta$, $|E_{\text{new}}|$, $S(t)$, $\Phi'(t)$), the decision and reason string, per-segment latencies, and transition timestamps. This record links every recovery path back to the guards in (\ref{eq:policy}) and supports post-hoc correlation with training-quality metrics under the paired-run methodology of \S\ref{sec:eval}~\cite{wohlin2012ese,arcuri2014hitchhiker}. The overhead of $\Phi'(t)$ accounting and log emission is $O(1)$ per iteration and empirically negligible (\S\ref{sec:rq4}).

\subsection{Implementation}
\label{sec:impl}

We implement MoEGambit as a 2{,}847-line Python patch atop Megatron-LM (commit \texttt{core\_r0.9.0}) with four modules: a safe-point controller (412 LoC) that hooks \texttt{MegatronOptimizer.step()}, a policy engine (198 LoC) that maintains $S(t)$ and evaluates Algorithm~\ref{alg:policy}, a hybrid-restore module (1{,}483 LoC) that implements path~P with \texttt{torch.distributed.broadcast} and path~C with rank-local \texttt{torch.load}, and a reintegration state machine (754 LoC) that re-derives expert routing and releases the Phase~B barrier.
The patch requires no changes to Megatron-LM's forward/backward kernels, parallelism configuration, checkpoint-save path, launcher, or daemon setup. It is enabled by a single \texttt{-{}-enable-moegambit} flag to \texttt{torchrun}; when absent, training follows the unmodified Megatron-LM path with zero overhead.



\section{Evaluation}
\label{sec:eval}

This section evaluates whether MoEGambit reduces recovery cost without degrading the post-recovery training trajectory. We ask six research questions:

\begin{itemize}
    \item \textbf{RQ1:} How much recovery cost does MoEGambit reduce, and do hybrid restore and two-phase recovery compose?
    \item \textbf{RQ2:} Does admitted hybrid recovery avoid detectable quality degradation relative to failure-free training?
    \item \textbf{RQ3:} Does $\Phi'(t)$ identify quality degradation under repeated and burst failures?
    \item \textbf{RQ4:} What overhead do the monitoring hooks add during failure-free training?
    \item \textbf{RQ5:} Does the recovery advantage hold across scale and parallelism layouts?
    \item \textbf{RQ6:} Does the mechanism generalize to a different MoE model configuration?
\end{itemize}

We use NoFault $\sigma_{\text{base}}$ bands as practical effect-size references and paired nonparametric tests to assess degradation; we do not require every individual recovered run to lie inside the $\pm1\sigma_{\text{base}}$ band.

\subsection{Compared Systems}\label{sec:compared}

We compare MoEGambit with three baselines: \textbf{NoFault} (no injected failures, reference trajectory); \textbf{Restart} (standard Megatron-LM checkpoint restart with full reload and replay); and \textbf{MoC-System} (the only previously published MoE-specific fault-tolerance system we are aware of~\cite{cai2024moc}).

\textbf{MoC-System.} MoC-System is a save-side MoE fault-tolerance system that reduces checkpointing cost with Partial Experts Checkpointing (PEC): each checkpoint stores only a selected subset of experts and rotates that subset across saves. Because no public reference implementation is available, we separate accuracy and timing. For accuracy, we reproduce the most favorable PEC configuration reported in the MoC-System paper ($K_{\text{pec}}=16$, $N=128$, PLT~$\approx 3.75\%$) by redirecting each non-fresh expert to its corresponding historical checkpoint shard, with MoEGambit's hybrid repair and two-phase protocol disabled. For timing, we use the most favorable published/derived recovery numbers from the paper; since MoC-System is save-side, recovery still resumes from checkpoint state and replays lost iterations to reach step $t$.

\subsection{RQ2: Training Quality and Stability}
\label{sec:rq2}

RQ2 tests the quality side of the recovery contract: does admitted hybrid recovery avoid detectable degradation relative to failure-free training?

\textbf{Setup.} Each run performs 1{,}000 warmup iterations, injects one failure, then continues for 1{,}000 iterations against paired NoFault and Restart runs. Gaps admitted by the contract ($\Delta\!\in\!\{64,128\}$) execute the hybrid path; larger forced gaps $\Delta\!\in\!\{256,512,1000,1500\}$ stress the per-event guard and route to restart unless the guard is deliberately disabled.

\textbf{Result.} For hybrid gaps admitted by the contract, paired validation loss and perplexity show no detectable degradation relative to NoFault/Restart. Fig.~\ref{fig:train-loss} shows the full 10{,}000-iteration trajectory under ten injected faults, and Fig.~\ref{fig:fault-heatmap} zooms into 50 admitted single-failure runs around the NoFault mean: 44/50 runs fall within $\pm2\sigma_{\text{base}}$ and 23/50 within $\pm1\sigma_{\text{base}}$. A Wilcoxon signed-rank test on the 10 paired eval-loss differences at iter~600 yields $p\!=\!0.63$ and Cliff's delta $=0.07$, giving no evidence of degradation. Larger forced gaps are used only as guard stress tests; under the default policy, those cases route to restart.

Because runs are paired by seed, data order, checkpoint, and failure time, the criterion is conservative: MoEGambit is judged by paired deviation from the baseline trajectory, not by whether a single noisy run improves a score.

\subsection{RQ3: Multiple Failures and Expert-Weighted Staleness Density}
\label{sec:rq3}

RQ3 validates the R2 specification: does the $\Phi'(t)\!\leq\!\Phi_{\max}$ guard correctly identify the quality-degradation boundary under multi-rank burst failures?

We evaluate MoEGambit under repeated and multi-rank burst failures and validate the $\Phi_{\max}=10^{-2}$ threshold from \S\ref{sec:policy}. Using \texttt{find\_multi\_fault.sh}, we sweep $|F|\!\in\!\{8,16,24\}$ burst failures across $\Delta\!\in\!\{50,100,150,200\}$ on the same $3\!\times\!4$ grid as Table~\ref{tab:multi_fault}, and include repeated-window traces that revisit the same rank within $W$. A gap-only or always-hybrid policy would treat these patterns alike; $\Phi'(t)$ separates them through $|E_{\text{new}}|$ and the accumulated window debt.

\textbf{Result.} Under the default policy, MoEGambit applies hybrid recovery on the seven $\Phi'(t)\!\leq\!10^{-2}$ cells and redirects the five over-threshold cells to checkpoint restart, where cell-mean loss returns inside the $\pm 1\sigma_{\text{base}}$ band. With the guard disabled, those same five cells reproduce the $1.21$--$1.98\sigma_{\text{base}}$ deviations in Table~\ref{tab:multi_fault}. Thus the above-threshold quality result comes from fallback, and the expert-weighted window captures risk missed by gap-only policies.

This result also explains why $\Delta_{\max}$ alone is insufficient. Two events with the same checkpoint gap can expose very different fractions of the expert population depending on which ranks fail and how recently other experts were repaired. $\Phi'(t)$ makes that exposure explicit by charging each event in proportion to both its gap and its affected expert set, then aging the charge out of the window. The guard distinguishes isolated single-rank failures from dense bursts even when their per-event gaps are identical.

\subsection{RQ4: Failure-Free Overhead}
\label{sec:rq4}

\textbf{Result.} Over 1{,}000 failure-free iterations, MoEGambit's hooks add $<6$\,\textmu s per iteration and change mean step time by only $+0.1\%$; a paired $t$-test does not reject a zero mean difference at $\alpha=0.05$.

\subsection{RQ5: Scalability}\label{sec:rq5}

We rerun the single-failure injection of \S\ref{sec:rq1} at 64 and 128 GPUs (TP$=$1, PP$=$8, EP$\in\{$8,16$\}$; 10 seeds each) and test four 64-GPU parallelism layouts spanning TP$\in\{1,2\}$, PP$\in\{4,8\}$, EP$\in\{4,8\}$, and EDP$\in\{1,2\}$. \textbf{Result.} Checkpoint restart grows with global checkpoint size ($36.4$\,s $\to 47.2$\,s), while MoEGambit grows more slowly ($28.9$\,s $\to 33.7$\,s) because hybrid I/O scales with the per-rank shard. The Restart/MoEGambit ratio widens from $1.26\times$ to $\mathbf{1.40\times}$ (Fig.~\ref{fig:scalability}), suggesting larger benefits at larger GPU scales where restart reloads and replays more global state.

\subsection{RQ6: Cross-Model Generalization}\label{sec:rq6}

To assess generalization beyond Qwen3-30B-A3B, we rerun the core single-failure and burst experiments on \textbf{DeepSeek-V2-Lite}~\cite{deepseekv2} (15.7B total / 2.4B activated, 64 routed experts, 2 shared experts, top-6). Shared experts are DP-replicated and recovered through path~P; only routed experts traverse path~C. Policy parameters are inherited from Table~\ref{tab:policy} with $N_{\text{expert}}\!=\!64$.

\textbf{Result.} Checkpoint restart takes $26.09$\,s while MoEGambit recovers in $11.73$\,s, a $55.0\%$ reduction ($2.22\times$). Smaller expert shards make path~C faster while path~P cost stays comparable; the burst sweep shows the same $\Phi'(t)=10^{-2}$ threshold, and routing shared experts through path~C reduces the advantage by $3.2$~pp.

\subsection{Threats to Validity}\label{sec:threats}

Following standard SE validity categories~\cite{wohlin2012ese}, we summarize the main threats. \emph{Internal validity.} Because no public MoC-System implementation exists, we use its most favorable PEC configuration and timing numbers, report raw latency separately from replay-inclusive speedup, and disable PEC when measuring MoEGambit's own mechanisms. Residual system noise from NCCL collectives, network timing, GPU/node heterogeneity, storage jitter, and kernel scheduling is controlled through paired seeds, identical data order/failure steps, and NoFault $\sigma_{\text{base}}$ bands. \emph{Construct validity.} Post-recovery quality is measured through loss, perplexity, and eight zero-shot tasks; other downstream uses may require additional probes. The $\Phi'(t)$ guard is conservative: over-threshold cases fall back to restart, so miscalibration sacrifices speed before quality. \emph{External validity.} Results cover two Megatron-LM MoE configurations on H20-3e interconnects. Other layouts, fabrics, checkpoint backends, failure detectors, or auxiliary-loss settings may change absolute speedups and require recalibrating $\Phi_{\max}$.

\section{Related Work}
\label{sec:related}

\textbf{Self-adaptive and self-healing systems.} The MAPE-K model~\cite{kephart2003autonomic}, architectural self-adaptation~\cite{garlan2004rainbow}, and SE roadmaps~\cite{cheng2009software,weyns2019softwareengineering} argue that runtime repair should be specified, guarded, and auditable. MoEGambit instantiates this view for MoE recovery: $\Phi'(t)$ governs when to adapt, the state-class boundary determines where, and hybrid restoration defines how. Its target is cumulative quality risk over a sliding window, not a point-in-time availability violation.

\textbf{Checkpointing, topology adaptation, and peer recovery.} Checkpoint systems reduce the cost $C$ in Young/Daly-style restart~\cite{young1974first,daly2006higher}, including CheckFreq~\cite{mohan2021checkfreq}, DeepFreeze~\cite{nicolae2020deepfreeze}, Check-N-Run~\cite{eisenman2022check}, Gemini~\cite{wang2023gemini}, REFT~\cite{wang2024reft}, and ByteCheckpoint~\cite{wan2024bytecheckpoint}. These systems preserve checkpoint-consistent recovery semantics. Topology-adaptation systems such as Bamboo~\cite{thorpe2023bamboo}, Oobleck~\cite{jang2023oobleck}, ReCycle~\cite{gandhi2024recycle}, Varuna~\cite{athlur2022varuna}, Parcae~\cite{duan2024parcae}, Litz~\cite{qiao2019litz}, and Or et al.~\cite{or2020resource} avoid reloading by reconfiguring around surviving ranks, but assume rank interchangeability. FlashRecovery~\cite{zhang2025flashrecovery} pulls a dense DP replica from a peer; MoEGambit applies peer recovery only to DP-replicated non-expert state and guards stale EP-sharded experts.

\textbf{MoE systems and fault tolerance.} GShard~\cite{lepikhin2021gshard}, Switch~\cite{fedus2022switch}, DeepSpeed-MoE~\cite{rajbhandari2022deepspeedmoe}, Tutel~\cite{hwang2023tutel}, FasterMoE~\cite{he2022fastermoe}, SmartMoE~\cite{zhai2023smartmoe}, MegaBlocks~\cite{gale2023megablocks}, and open MoE models~\cite{jiang2024mixtral,dai2024deepseekmoe,deepseekv3,qwen3report} optimize routing, dispatch, and all-to-all efficiency; ST-MoE~\cite{zoph2022stmoe}, sparse-upcycling~\cite{komatsuzaki2023sparse}, and V-MoE~\cite{riquelme2021vmoe} develop MoE architectures. They leave expert freshness as an implicit invariant. MoC-System~\cite{cai2024moc} reduces save-side cost with Partial Experts Checkpointing but still resumes from checkpoint state; MoEGambit targets recovery-side replay, load cost, and runtime quality gating.

\section{Discussion}
\label{sec:discussion}

\textbf{Implications.} Reliable MoE recovery should be state-aware and auditable. Treating the job as a uniform checkpoint object forgoes a $20$--$55\%$ latency reduction, and the advantage grows when global checkpoint state grows faster than per-rank expert shards. A gap-only rule ignores accumulated expert exposure; R1--R3 provide observable guards, fallback reasons, and logs that make each low-latency decision testable.

\textbf{Why not a gap-only heuristic.} A small $\Delta$ can be risky after repeated repairs, while a larger isolated gap may touch only a small expert fraction. The contract therefore exposes both the admission predicate and the measured debt $S(t)$, making every fast-path decision falsifiable against the subsequent paired quality trace.

\textbf{Deployment and composition.} MoEGambit keeps checkpoint restart as the conservative fallback. Operators can first run the policy in audit-only mode, compare logged decisions with the local noise floor, and enable hybrid admission only after $\Phi_{\max}$ is calibrated. Save-side checkpoint optimizations remain complementary: they can shrink $\Delta$, while MoEGambit still avoids full-state reload and replay when the guard admits recovery.

\textbf{Operational interpretation.} The structured log makes each recovery decision inspectable rather than an opaque restart shortcut. Operators can distinguish peer-unavailability fallbacks from staleness-cap fallbacks, replay the guard inputs offline, and correlate later loss movement with the recovery decision that produced the state.

\textbf{Limitations and future work.} MoEGambit requires a healthy DP peer at the failed rank's PP/TP coordinate; correlated failures fall back to restart. The $\Phi_{\max}=10^{-2}$ threshold is calibrated for the evaluated auxiliary-loss settings, although RQ6 shows the same threshold on DeepSeek-V2-Lite. The implementation assumes static expert placement and fail-stop failures; dynamic migration~\cite{he2022fastermoe}, slow degradation, silent data corruption~\cite{chowdhery2023palm}, and network partitions require additional guards. Future work will add expert-usage statistics and online noise-floor estimates so the guard can be stricter for hot experts and less conservative for cold experts.

\section{Conclusion}
\label{sec:conclusion}

MoEGambit treats failure recovery in distributed MoE training as a contract-governed runtime subsystem. Its safe-point controller, staleness guard, and reintegration log separate \emph{when} partial repair is allowed from \emph{how} state is repaired. MoEGambit reduces raw recovery latency by $20.6\%$--$55.0\%$, achieves a $36.9\times$ replay-inclusive speedup, and shows no statistically detectable quality degradation for failures admitted by the contract.
